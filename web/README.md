# CW Decoder (Web)

ブラウザで動く CW Decoder です。**ESP32 版とまったく同じ DSP / デコーダ**を
WebAssembly でそのまま実行します。ハードウェアは要りません。

## 動かす

```sh
sh web/serve.sh
```

サーバーを立てて <http://localhost:8777/> を開きます (ポートは引数で変更可)。
`cwcore.wasm` はビルド済みで入っているので、これだけで動きます。

### サーバーは必須です

**`file://` でファイルを直接開いても動きません。** AudioWorklet のモジュールは
サーバー経由でしか読み込めないためです。`file://` はページのオリジンが
`null` (不透明) になるので、ワークレットのソースが外部ファイルでも、
埋め込んだ Blob (`blob:null/...`) でも data: URL でも、すべて cross-origin と
判定されて拒否されます (`AbortError: ... a dependency or cross-origin script
failed to load`)。マイク入力も `file://` では許可を保持できません。

`https` か `localhost` なら問題ありません。GitHub Pages などに `web/` を
そのまま置けば公開できます。

### 単一ファイル版

`web/cw-decoder.html` (72KB) は app.js・ワークレット・wasm をすべて 1 枚に
埋め込んだものです。**これも `file://` では動きません** (上記のとおり) が、
他のファイルを一切置かずに静的ホストへ 1 枚だけ置けば動くので、配布用に使えます。

`sh web/build.sh` で自動生成されます。wasm を作り直す必要がないときは
`python3 web/bundle.py` だけでも生成できます (git には含めていません)。

## 音声の入力元 (画面上部のタブで切り替え)

| 入力元 | 用途 | 備考 |
|---|---|---|
| **マイク / ライン入力** | 無線機の音を実際にデコードする | USB オーディオ I/F が最も確実。仮想ループバック (BlackHole / VB-CABLE) で PC 内部の音も拾える |
| **タブ音声** | WebSDR や動画をそのままデコード | Chrome 系のみ。共有ダイアログで「タブの音声も共有する」を ON にすること |
| **音声ファイル** | 録音を再生してデコード | 同じ音源で何度でも再現できるので、設定を比べるのに使える |
| **テスト信号** | ハード無しで動作確認 | WPM / トーン / S:N を振れる内蔵 CW 発生器 |

**エコーキャンセル・ノイズ抑制・AGC は自動で無効化しています。**
これらが有効だとブラウザが CW を「ノイズ」とみなして消してしまい、まったく
デコードできません。それでも一部の環境 (特にモバイル Safari) は完全には
無効化できない場合があります。

## 実機との違い

ESP32 版のうち、ブラウザでは意味を持たない機能は載せていません。

- 時計画面 / NTP 同期 / 時刻合わせ — ホストの時計を使えばよい
- WiFi 設定 / OTA — 再読み込みが更新にあたる
- タッチ調整 — ポインタ座標がそのまま使える
- スコープログ (シリアル) — 出力先がない

信号処理まわりで挙動が変わるのは入力レベル表示だけです。実機の 0 dBFS は
「ADC 半スイング ≈ 1.55V ピーク」でしたが、こちらはデジタルフルスケール基準に
なります。黄の目盛 (ESP32 の ADC の直線範囲の上限) も意味を失いますが、
デジタルクリップの警告としては引き続き有効です。

デコーダのしきい値はノイズ床基準の相対値なので、入力レベルが多少変わっても
デコード率は変わりません。

## 実機より認識率が悪いときに見るところ

上から順に確認してください。**1 が圧倒的に効きます。**

### 1. 入力BPF (実機のアナログ BPF 相当) — 既定 ON

実機は ADC の手前に**多重帰還型バンドパス (中心 700Hz / Q=5)** が入っています。
ファームウェアの振幅しきい値・ノイズ床推定・サイドビン判定は、その帯域制限された
入力を前提に実機で調整されたものです。Web 版には素の全帯域音声が入るので、
この BPF が無いと帯域外ノイズがノイズ床とサイドビンを押し上げ、デコード率が大きく落ちます。

実測 (ノイズ混じりの CW 録音 77 秒、正解文との文字一致率):

| 条件 | 正解率 |
|---|---|
| **BPF なし** | **44%** |
| BPF 700Hz Q=5 (実機のハードと同じ) | **93%** |
| **BPF 700Hz Q=3 (Web 版の既定)** | **97%** |
| BPF 650Hz Q=2 | 97% |
| BPF 750Hz Q=2 (2段) | 99% |

デコード結果の違い:

```
BPF なし : ALICE WAS BEGINNING TO GET VERY TIRED OF SITTITETN BTD IEER SE EIIEET TTTN ...
BPF あり : ALICE WAS BEGINNING TO GET VERY TIRED OF SITTING BY HER SISTER ON*E BANK, AND ...
```

上の実測はノイズ混じりの CW 録音を「音声ファイル」タブから読ませたものです
(音源はリポジトリに含めていません。後述)。再生中に **入力BPF** を
切り替えると、その場で差が見られます。

既定は **700Hz 固定 / Q=3** です。中心周波数は実機と同じ、Q は実機 (Q=5) より
少し下げてあります。理由は下記。

#### なぜ前段のフィルタが効くのか

トーン判定の Goertzel は既に 67Hz の帯域で見ているので、その手前に 233Hz
(Q=3) の緩いフィルタを足しても中心ビンの SN 比はほとんど変わらないはずです。
実際、測ってみるとマーク中のマグニチュードはむしろ下がります。
**効いているのはサイドビン比でも中心の SN 比でもなく、相対スケルチです。**

同じ録音 (トーン 600Hz) でのデコーダ内部値の中央値:

| | BPF なし | BPF 700Hz Q=3 |
|---|---|---|
| マーク中の mag | 3901 | 3299 |
| **ノイズ床 (nf)** | **626** | **344** |
| **スケルチ床 (nf x8)** | **5008** | **2752** |
| magnitudelimit | 5088 | 3293 |
| 中心/遠サイド | 20.0dB (必要 9.5) | 23.7dB |
| 中心/近サイド | 16.2dB (必要 6.0) | 20.1dB |
| **ON しきい値への余裕 (中央)** | **2.4dB** | **4.5dB** |
| 「短すぎ」で捨てたマーク | **13 個** | **5 個** |

サイドビン比は BPF が無くても必要値を大きく上回っており、**一度も制約に
なっていません**。制約になっているのは `decoder.cpp` のこれです。

```c
int32_t limit_floor = noise_floor * NOISE_SQUELCH_X10 / 10;   // x8
if (magnitudelimit < limit_floor) magnitudelimit = limit_floor;
```

BPF が無いとノイズ床が 626 まで上がり、**スケルチ床 5008 がマークの振幅
3901 を上回ります**。`magnitudelimit` は床に張り付き、ON 条件
`mag > 0.6 x limit` のしきい値が 3053 まで持ち上がって、余裕がわずか
2.4dB しか残りません。帯域内ノイズとトーンのうなりによる振幅の谷が
この薄い余裕を食い潰し、58ms のマークが 19ms の断片になって
「短すぎ (< 0.6 単位)」で捨てられます。

つまり**前段フィルタは信号を綺麗にしているのではなく、デコーダが自分で
決めるしきい値を下げさせている**わけです。ノイズ床推定は「トーンらしくない
ブロック」を取り込んで作られるので、帯域外のノイズが減ると推定値が下がり
(626 → 344、-5.2dB)、それが x8 されてそのまま ON しきい値の -5.2dB になります。

なお「ならばスケルチ倍率 (x8) を下げればよいのでは」は**実測で否定済み**です
(下の「効果が無かった案」)。床を下げると隙間のノイズで再点火して偽符号が出ます。
**BPF は床そのものを下げるので、倍率を緩めずに同じ余裕が得られる** —
これが倍率調整より BPF のほうが優れている理由です。

#### Q を上げすぎてはいけない理由

デコーダは「純音かどうか」を中心ビンとサイドビン (±133Hz / ±267Hz) の
**比 = スペクトルの傾き**で判定しています ([src/decoder.cpp](../src/decoder.cpp) の `tone_on`)。

```
ON 条件: 中心 > 遠サイド(±267Hz) x 3   → 9.5 dB の落差が必要
         中心 > 近サイド(±133Hz) x 2   → 6.0 dB の落差が必要
```

ところが**狭い BPF は、まさにその落差を自分で作ってしまいます**。ノイズを
通しただけで中心とサイドに差がつくので、デコーダから見ると純音と区別が
つきません。CW を一切含まない純ノイズ 60 秒を通したときの偽文字数:

| Q | 帯域幅 | 遠サイド落差 | 近サイド落差 | ON条件 | 偽文字/分 |
|---|---|---|---|---|---|
| 1 | 700Hz | 1.6 dB | 0.5 dB | 満たさず | **0** |
| 2 | 350Hz | 4.4 dB | 1.7 dB | 満たさず | **0** |
| **3** | **233Hz** | **6.9 dB** | **3.2 dB** | **満たさず** | **0** |
| 5 | 140Hz | 10.7 dB | 6.1 dB | 両方成立 | 8 |
| 8 | 88Hz | 14.6 dB | 9.5 dB | 両方成立 | 144 |
| 12 | 58Hz | 18.0 dB | 12.7 dB | 両方成立 | 241 |

偽符号が立ち上がる点が「フィルタ自身の落差がしきい値を超える点」と一致します。
**臨界条件は、BPF の帯域幅がサイドビンの間隔 (±133 / ±267Hz) を下回ること**です。
Goertzel のサイドビンは矩形窓のヌル上に置いてあって純音には反応しない設計ですが、
その手前のフィルタが同じ形の傾きを作ると前提が崩れます。

Q=3 は「偽符号ゼロを保てる範囲で最大の帯域削減」にあたります。
逆に Q=1 まで下げるとノイズをほとんど削れないので、これも悪化します。

なお**リンギングは主因ではありません**。立ち上がり時間は Q=5 で 5.9ms、
Q=12 で 14.3ms (20WPM の短点 60ms の 10% / 24%) ですが、クリーン信号では
Q=8 まで全速度で 100%、Q=12・40WPM でようやく 83% に落ちる程度でした。

700Hz から離れたトーンを受けるときは **トーン追従** を選ぶと中心が同調先へ動きます
(実機には無い動作です)。

#### 参考: なぜ 3 ビン判定でノイズに強くなるのか

前段 BPF とは別の話だが、しきい値をいじるときに前提になるので測った結果を残す。

3 ビン判定は周波数を測っているのではなく、**エネルギーが 1 点に集中しているか**を
測っている。サイドビンは矩形窓 Dirichlet 核のヌル上に置いてあるので、純音は
サイドへ漏れない:

```
純音 700Hz を 120 サンプル窓に入れたとき
  中心             59.9
  遠サイド(±267Hz)  0.12   → 中心比 54dB
  近サイド(±133Hz)  0.09   → 中心比 56dB
```

ノイズは全帯域に散らばるので中心もサイドも同程度になる。つまり
「中心 >> サイド」がそのまま「純音か否か」の判定になる。
**ノイズが単一周波数でないからこそ差がつく**。

ただし **1 ブロック (120 サンプル = 15ms) の実測ではノイズのスペクトルは
平坦ではない**。ばらつきが大きく、偶然サイドが低く出るブロックがある:

| 入力 | 中心/遠サイド比 (10% / 中央 / 90%) | ON 条件を満たす割合 |
|---|---|---|
| 純ノイズ | -8.5 / 0.4 / **+8.0** dB | **6.4%** |
| 信号+ノイズ (-3dB) | 5.7 / 10.9 / 17.1 dB | 63.2% |
| 純音 | 54.1 / 60.0 / 65.1 dB | 100% |

だからファームは 1 ブロックの判定を信用しない造りになっている
(サイドの EMA 平滑、L と H の幾何平均、近サイドと遠サイドの両方、
振幅条件との同時成立、ノイズブランカの積分)。偶然の集中が全部そろう
確率は急速に小さくなる。

#### 3 ビンの効果と限界 (サイド条件を殺した版との比較)

サイド条件をすべて無効化した wasm (振幅しきい値のみ = 単一ビン相当) を
ビルドして比べた。合成 CW 20WPM、4 シードの平均:

| S/N | 3 ビン (現行) | 振幅のみ | 差 |
|---|---|---|---|
| 20dB | 100% | 100% | 0 |
| 10dB | **100%** | 96% | +4pt |
| 6dB | **100%** | 89% | **+11pt** |
| 3dB | **100%** | 95% | +5pt |
| 0dB | **100%** | 94% | +6pt |
| -3dB | **99%** | 95% | +4pt |
| **-6dB** | **42%** | **63%** | **-21pt** |

実用域 (10dB〜-3dB) では一貫して 3 ビンが勝つが、**-6dB では逆転する**。
低 S/N では信号自身の比もノイズの比に近づくので、サイド条件が本物のマークまで
弾くようになる (出力を見ても実際に崩れている)。

```
-6dB  3ビン : E5V CQ CQ DE EOAWAAN C AMA1TBNTE K
-6dB  振幅  : E EVV CQ CQ DE JA*ANEC AMA1ABC K
```

**予想が外れた点を 2 つ記録しておく。**

1. **無信号時の偽符号はどちらも 0 個/分だった。** 3 ビンの主目的が無信号時の
   誤検出抑止だと考えていたが、純ノイズに対しては相対スケルチ (ノイズ床 x8)
   だけで足りていた。ノイズ床がノイズに追従するのでノイズ自身が超えられない。
2. **要素の融合も起きなかった。** `decoder.cpp` のコメントに「キーイングの
   ギャップの解除もこの条件が担う」とあるので疑ったが、送信 77 マークに対し
   検出 74〜78、3 単位を超える融合は両者とも 0 件。

つまり 3 ビンの効きは「無信号時の誤検出」でも「要素の融合」でもなく、
信号がある最中のブロック単位のエッジ判定の精度として現れているらしい。
**ここは追いきれていない。**

### 2. ch 選択 (ステレオ入力のとき)

**ステレオ I/F の片チャンネルだけに無線機を繋いでいる場合、`L+R` にすると
空いている側のノイズを足し込むので大きく劣化します。** 実機は入力がモノラル
1 系統なのでこの問題が起きません。必ず信号の載っている `L` か `R` を選んでください。

合成 CW での実測 (20WPM / 700Hz、L に信号・R は空き):

| R の状態 | S/N | L のみ | L+R |
|---|---|---|---|
| 空き (同等ノイズ) | 3 dB | 100% | 97% |
| 空き (同等ノイズ) | 0 dB | **100%** | **0%** |
| 空き (ノイズ2倍) | 6 dB | 100% | 90% |
| 空き (ノイズ2倍) | 3 dB | **100%** | **0%** |

### 3. 入力レベル

レベルメーターが黄〜赤なら **入力ゲイン** を下げてください。ESP32 の ADC は
-5.2 dBFS より上で非線形になり、サイドビンが上がってデコード率が落ちます
(この関係は Web 版でも同じです)。`CLIP` が点いていなくても、黄より右は過大です。
目安は -24〜-12 dBFS あたりです。音声ファイルは読み込み時に -12 dBFS へ
自動調整しますが、マイク / ライン入力は手動です。

### 4. ブラウザの前処理が本当に切れているか

マイク入力を開始すると、状態行に実際に適用された設定が出ます。

```
マイク/ライン: USB Audio CODEC — 48000Hz / 2ch → L / 前処理なし
```

ここに `⚠ noiseSuppression が無効化できていません` のように出たら、
ブラウザが要求を受け入れていません。CW が「ノイズ」として消されるので、
別のブラウザ (Chrome 系) を試してください。

### 5. 実効入力レート (sps)

状態行の右に出ます。**正常は 8000 sps** です。ここが赤くなって 8000 を
割っている場合、オーディオスレッドが締め切りに間に合わず入力を
落としています (符号長が狂うので WPM 推定ごと崩れます)。
他の重いタブを閉じる、モニター音を切る、などを試してください。

### 確認済みで原因にならないもの

- **48kHz → 8kHz のデシメート**: 実機の「32kHz を 4 点平均」と同じ箱型で、
  8kHz 出力に対するヌルの位置も通過帯域の落ち込み (1kHz で -0.2dB) も一致します
- **サンプルの取りこぼし**: 実測で 8000 sps ちょうど (上の 5 で確認できます)
- **受信開始直後の 1 文字目**: 振幅しきい値の EMA と速度推定が収束する前に
  当たるので化けます。これは実機と同じ挙動です

### 表示が止まるとき

タブや Browser ペインが隠れるとブラウザが `requestAnimationFrame` を止めるので、
画面の更新は止まります。**デコード自体は AudioWorklet 側で動き続ける**ので、
戻れば溜まった文字がそのまま出ます (意図した設計です)。

## 誤認識の調査記録

ノイズ混じりの実録音で誤っていた 3 文字を追いかけた記録
(音源はリポジトリに含めていない)。
同じ調査を繰り返さないために、**効果がなかった案も残してある**。

### 症状

```
正解: ... HER SISTER ON THE BANK, AND OF HAVING NOTHING ...
誤り: ... HER SISTER ONTH SANK,   AND MF HAVING NOTHING ...
```

`THE` の `E` が消え、`BANK` の `B`(-...) が `S`(...) に、`OF` の `O`(---) が
`M`(--) になっていた。いずれも**要素が 1 つ落ちる**形。

### 切り分け

1. **ノイズ無し版との比較**: 同じ内容のノイズ無し版 (前半 32 秒) は
   100% 正解。ノイズ有り版も**その範囲では 100% 正解**で、誤りは全て
   32 秒以降に集中していた
2. **要素長の実測** (`cw_elem_*` で取得): 落ちた要素は 58ms あるはずが
   **19ms / 34ms の断片**としてしか記録されず、「短すぎ (< 0.6 単位)」で
   捨てられていた
3. **音声そのものの包絡線**: 該当箇所には振幅 93%・幅 146ms の明瞭な
   マークが存在した。つまり**信号はあるのにデコーダが取れていない**
4. **AUTO 同調の追跡**: 35.5〜36.1s の 0.6 秒間、ゲート中心が
   **600Hz → 650Hz へ飛んでいた**。落ちた文字はちょうどこの区間

### 原因

ゲートの検出帯域は 67Hz (±33Hz) なので、50Hz ずれると信号が帯域外に出る。
デコーダから見ると信号が消えたのと同じで、マークが断片としてしか拾えない。

飛んだ理由は `DSP_AUTO_NEAR_HZ` が **70Hz** だったこと。これは
「ゲート OFF のとき、このズレ以下なら無条件で追従する」という値で、
帯域端にかかった信号を引き戻すためのもの。しかし **70Hz はゲートの
半値幅 (±33Hz) の 2 倍以上**あり、信号が完全に帯域外へ出る距離まで
無条件の乗り換えを許していた。符号間・文字間・語間はゲート OFF なので、
その隙間にノイズのピークが立つと持っていかれる。

### 対策

`src/dsp.cpp` の `DSP_AUTO_NEAR_HZ` を **70 → 35** (ゲートの半値幅に合わせる)。
これを超えるズレには従来どおりホールド比 1.5 倍の条件が課される。

| 条件 | 70 (旧) | 35 (現行) |
|---|---|---|
| **実録音 (ノイズ)** | **97%** | **99%** |
| 実録音 (ノイズ無し) | 100% | 100% |
| 合成 20WPM / 3dB | 100% | 100% |
| 合成 35WPM / 10dB | 97% | 97% |
| 合成 45WPM / 15dB | 88% | 88% |
| 純ノイズ 60 秒の偽文字 | 0 | 0 |

誤り 3 箇所がすべて解消し、退行は無し。残るのは `ON` と `THE` の間の語間のみ。

### 効果が無かった案 (実測済み・再検討不要)

| 案 | 結果 |
|---|---|
| 相対スケルチを緩める (ノイズ床 ×8 → ×6, ×5) | **悪化** 97%→95〜96%、偽文字 1〜12 個/分。床を下げると隙間のノイズで再点火する。同じ余裕は入力BPF で床そのものを下げて得るほうがよい ([なぜ前段のフィルタが効くのか](#なぜ前段のフィルタが効くのか)) |
| 近サイド OFF 比を緩める (3.2 → 2.8 / 2.5 / 2.2) | 変化なし |
| 遠サイド OFF 比を緩める (2.5 → 2.0) | 変化なし |
| ノイズブランカ上限 (5 → 7 / 9 / 12 / 16 ブロック) | 変化なし |
| 入力 BPF の中心を信号周波数に合わせる | 明確な傾向なし (84〜99% でばらつく) |

**デコーダのしきい値定数は現状が最適**で、スケルチを下げると偽符号が出る。
これは `src/decoder.cpp` のコメントが warning していたとおりだった。

### 調査に使った道具

- `cw_elem_*` … 要素 (マーク/スペース) の実測長と単位長推定。
  スコープ列は多数決で量子化されるので、タイミングの検証にはこちら
- スコープ列の後半 8 バイト … `limit` / `nf` / `side` / `near`。
  しきい値割れかサイドビンの持ち上がりかを見分ける
- ステータスの `tone_hz` … AUTO の同調先。今回はこれが決め手だった

## ビルド

`cwcore.wasm` を作り直すときだけ必要です。

```sh
brew install lld     # wasm-ld が入る (初回のみ)
sh web/build.sh
```

Emscripten は使いません。中核コードは STL もヒープも使わず、必要な数学関数も
`cosf` / `sinf` / `sqrtf` / `sqrt` の 4 つだけなので、clang の wasm32 ターゲットと
`wasm-ld` によるフリースタンディングビルドで通ります (出力は約 13KB)。

### テスト用の音声について

`web/tools/` に置いた音声ファイル (`*.mp3` / `*.wav`) は **`.gitignore` 済みで
リポジトリには含めていません**。下の調査記録が参照しているファイル名は、
その調査を行ったときに手元へ置いていたものです。

- `Vol20_Sig50_Noise100.mp3` … ノイズ混じりの CW 録音 (77 秒)。
  内容が Alice in Wonderland の冒頭なので正解文が分かり、文字一致率を出せる
- `original.mp3` … 上と同じ内容のノイズ無し版 (32 秒)。
  ノイズ下の誤りが「信号の癖」か「ノイズによる判定の乱れ」かを切り分ける基準

同じ手順を再現したいときは、任意の CW 録音を `web/tools/` に置いて
「音声ファイル」タブから読ませてください。正解文の分かる音源を使うと
`selftest.mjs` と同じ文字一致率で比較できます。

`src/dsp.cpp` / `src/decoder.cpp` / `src/decode.cpp` / `lib/float_fft` は
ファームウェアと**同じファイルを共有**しています。片方だけ直して挙動がずれる、
ということが起きないようにするためで、`web/` 側には信号処理のロジックを
一切置いていません。

## 回帰試験

```sh
node web/tools/selftest.mjs
```

合成 CW (WPM / トーン / S:N を変えたもの) を WASM 中核に食わせて、
デコード結果を文字単位で照合します。ブラウザもマイクも要りません。
しきい値やノイズ対策を触ったときは、これを通してから実機に焼くと安全です。

```
  wpm  tone   snr | 推定wpm  正解率  デコード結果
   15   700   30dB |     15    100%  CQ CQ DE JA1ABC JA1ABC K
   20   700    3dB |     20    100%  CQ CQ DE JA1ABC JA1ABC K
   35   700   20dB |     33    100%  CQ CQ DE JA1ABC JA1ABC K
```

なお、受信開始直後の 1 文字目は振幅しきい値の EMA と速度推定が収束する前に
当たるので化けることがあります (実機と同じ挙動)。試験では先頭にウォームアップの
1 語を置き、そこを除いて採点しています。

ノイズの乱数は固定シードなので、同じコマンドは常に同じ結果になります
(毎回違うノイズだと数%ぶれて、しきい値をいじった効果なのか運なのか
区別がつきません)。別の系列で確かめたいときは `--seed <n>` を付けてください。
